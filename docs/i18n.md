# 国际化维护约定

本文说明语言偏好、任务语言快照及应用消息资源的维护方式。具体 API 以 `src/language.rs`、`src/ui_i18n.rs` 和调用处源码为准；本文不作为完整 UI 验收记录。

## 1. 两个独立的语言偏好

| 偏好 | 选项与持久化 ID | 默认值 | 作用 |
| --- | --- | --- | --- |
| 界面语言 `UiLanguagePreference` | 跟随系统 `system`、简体中文 `zh-CN`、英语 `en` | `system` | 应用自有界面文字、提示及新 AI 任务的自然语言输出目标 |
| AI 提示词语言 `PromptLanguagePreference` | 跟随界面 `follow-ui`、简体中文 `zh-CN`、英语 `en` | `follow-ui` | 应用构造的 AI 指令、上下文说明和工具说明语言，不独立决定结果语言 |

偏好保存在现有 SQLite 数据库的 `language_preferences` 表，通过 `AppStorage` 读取和单字段更新。新增用户及没有偏好记录的旧数据库使用上述默认值。未知持久化 ID 分别回退为跟随系统、跟随界面；界面加载失败时记录日志并使用默认偏好。设置保存成功后才更新内存；不要让保存失败的选择改变当前运行语言。

当前实际支持的 `Language` 为 `ZhCn` 和 `En`。系统语言匹配按首选列表顺序取第一个支持项：

- `en` 及其地区变体匹配英语。
- 明确包含 `Hans`、`CN` 或 `SG` 的中文匹配简体中文；显式 `Hant`、`TW`、`HK`、`MO` 不匹配简体。
- 无支持项、列表为空或检测失败时回退简体中文；不把裸 `zh` 或繁体中文猜成简体。

Windows 读取用户 UI 首选语言列表，不使用格式区域代替；macOS 读取 `AppleLanguages`；其他平台先读取 `LANGUAGE` 有序列表，否则依次采用 `LC_ALL`、`LC_MESSAGES`、`LANG` 中首个非空值。

**跟随系统不是实时订阅。** 应用启动时解析一次；在设置中选择或重复选择跟随系统时重新检测。应用运行中仅修改操作系统语言，不会自动触发应用切换。

应用内切换界面语言会同步设置 Kit locale 和 `ui_i18n` 当前语言并刷新窗口。Windows 原生托盘不依靠 GPUI 重绘，语言切换入口另外调用 `TrayController::refresh_language()`，只更新现有菜单标签，不改变菜单业务 ID 或事件连接。

## 2. AI 的 system / output 分离与任务快照

在任务启动入口创建 `TaskLanguages::new(ui_language, prompt_preference)`，按值传入后台任务：

- `system`：提示词偏好解析后的语言，负责应用自有系统指令及相关说明。
- `output`：任务启动时的界面语言，负责自然语言结果目标。
- `output_instruction()`：使用 system 语言明确要求模型按 output 语言回答，同时保留代码、标识符、路径和 JSON 契约键。

例如，英语系统提示词配合中文界面时，应发送英语指令并明确要求简体中文结果，而不是把两种偏好合并成一个语言开关。实际模型输出仍需按任务契约验证，指令本身不保证模型一定遵守。

任务开始后切换偏好，只影响后续启动的任务。进行中的评审、重试、分段生成或工作流 Skill 应继续使用自己的语言快照，不能在循环中重读全局偏好。兼容包装函数可能使用 `TaskLanguages::default()`；新的应用任务入口应优先使用显式 `*_with_languages` 接口，避免意外固定为默认中文。

用户写入的提示词、代码、提交信息、工作流内容及已生成结果是数据，不因设置切换而重写。不要用翻译历史结果的方式实现切换语言。

## 3. 新增稳定消息资源

在所属页面或领域资源模块声明 `UiMessage`，复用既有资源组织方式。领域资源示例位于 `src/domain_ui_resources.rs`，由 `src/types.rs` 挂载；页面资源位于相应资源模块或 `src/ui_resources/`。不要为一个局部消息引入新的全局中文原文查表。

```rust
use crate::ui_i18n::UiMessage;

pub const OPEN_FAILED: UiMessage = UiMessage::new(
    "example.open_failed",
    "无法打开 {path}：{error}",
    "Could not open {path}: {error}",
);
```

维护规则：

1. key 表达稳定语义，不使用中文或英文译文作为 key；修改措辞不应改变业务身份。
2. 中英文使用同一组具名参数，优先翻译完整句子，不用片段拼接假设两种语言词序一致。
3. 当前不带参数的文字使用 `text(message)`，返回 `&'static str`；带参数使用 `format(message, &[("path", path), ("error", error)])`。
4. 显式语言场景和测试使用 `text_in(language, message)`、`format_in(language, message, args)`，不要临时切换全局语言。
5. 英文模板为空时显示回退中文，但新增资源应补齐双语，并加入所属资源注册表，通过 `validate` 校验非空、key 唯一及双语参数一致。
6. 参数不是 Rust 格式字符串：先将数字或复杂对象转换为字符串，再传具名参数。参数值不会被再次插值；路径中的 `{error}` 等内容必须保留原样。占位符缺失会原样保留，不能依赖这种行为掩盖漏传参数。

显示文案不得决定业务分支。优先匹配领域枚举、错误码或稳定消息 key，不比较 `Display` 结果，不使用 `contains("某段译文")` 判断是否取消、是否冲突或是否应回退视图。

## 4. 长驻状态、编码消息与显式消息槽

### 优先保留结构化类型

可以调整类型边界时，使用 `LocalizedMessage` 保存资源身份与原始参数，显示时调用 `resolve()`。领域错误使用 `GitError::Localized` 或 `GitError::LocalizedCredential`；已有专用错误变体、Git/IO 错误来源及业务错误码应继续保留。

`GitError::message_key()` / `is_message(key)` 用于稳定身份检查，`display_in(language)` 用于显式语言显示和测试。不要为国际化把已有语义变体全部降级为 `Message(String)`。

### 必须沿用 String 状态时

后台进度、通知或其他既有 String 状态可使用：

```rust
let status = crate::ui_i18n::encode(OPEN_FAILED, &[
    ("path", path),
    ("error", external_error),
]);
// 在用户可见的显示边界解析，而不是把编码文本直接交给控件。
let visible = crate::ui_i18n::resolve(&status);
```

编码状态保留 key、双语模板及原始参数。显示边界按当前语言解析，因此切换语言不需要重启任务或覆盖原始状态。普通字符串和无法识别的编码保持原样。需要固定语言时使用 `resolve_in(language, value)`；稳定身份通过 `message_key(value)` 取得。

必须核对全部消费边界：例如索引 `IndexProgress.message` 在生成处 encode，UI 和 MCP 的显示处 resolve。不要把内部编码标记暴露给用户、模型工具结果或外部程序。

### 嵌套应用消息必须声明消息槽

`encode` 的所有参数都是普通数据，即使参数恰好包含内部消息前缀，也不会递归解释。外层提示需要包裹另一条应用消息时，使用 `encode_with_messages(message, data, messages)` 显式声明：

```rust
const ACTION_FAILED: UiMessage = UiMessage::new(
    "example.action_failed",
    "操作 {path} 失败：{reason}",
    "Operation on {path} failed: {reason}",
);
let detail = crate::ui_i18n::encode(OPEN_FAILED, &[
    ("path", path),
    ("error", external_error),
]);
let status = crate::ui_i18n::encode_with_messages(
    ACTION_FAILED,
    &[("path", path)],             // 用户数据，不递归解析。
    &[("reason", detail.as_str())], // 明确属于应用消息，可随语言重译。
);
```

仅将可信的应用消息放进 `messages`，不要将外部错误、用户正文或工具原文当成消息槽。数据槽和消息槽使用不同参数名。当前递归有深度保护，不应构造深层消息链。

## 5. 数据、协议与持久化边界

只翻译应用拥有的自然语言，不翻译或改写：

- 用户输入、提交正文、仓库内容、文件名、路径、分支/标签名、凭据显示名称。
- 系统 Git、libgit2、外部工具、远端服务返回的原始错误正文。
- 协议方法名、工具名、JSON 契约键、schema 标识、状态码及业务 ID。
- 已持久化的用户名称及自动名称身份，不因显示语言变化重新生成。
- 日志和开发诊断无需作为界面资源迁移。

允许翻译包裹这些数据的应用自有句子，但参数必须原样保留。原有英文协议或面向模型的工具契约不能仅因其包含自然语言就盲目改写。

持久化状态优先保存稳定代码，显示时映射资源。索引覆盖原因采用 `coverage.reason` 稳定 reason code；`normalize_coverage_reason` 只在兼容边界识别旧版本已知的中文原因，未知工具原因原样返回。`coverage_reason_label[_in]` 提供显示，覆盖查询返回稳定 `reason` 与显示用 `reason_text`。新增原因需要同时覆盖写入代码、显示资源及旧数据兼容测试；不要重新把当前译文写进 reason。

## 6. 测试与验收

测试按现有结构放在 `src/tests/`，由所属模块通过 `#[path]` 挂载。主要参照：

- `src/tests/language.rs`：系统语言规范化、首选列表回退及任务快照组合。
- `src/tests/language_resources.rs`、`src/tests/ui_i18n.rs`：双语模板、参数、编码状态及显式嵌套消息槽。
- `src/tests/domain_ui_resources.rs`：资源校验、错误身份、双语显示和原始数据保护。
- `src/tests/code_index_coverage_i18n.rs`：稳定原因、旧中文兼容及未知工具原文。
- AI、工作流、OAuth 等所属测试：任务语言快照、契约保持、成功回调 HTML 等具体行为。

新增测试应同时检查中文、英文和原始参数不变；优先显式传入 `Language`，不使用并行测试共同修改全局 `set_language`。资源测试调用所属注册表的 `ui_i18n::validate`；身份测试检查枚举、错误码或 key，不以某种语言的文案替代身份断言。

按改动范围统一运行项目规定的检查，避免多个代理并发争用 Cargo：

```text
cargo check --all-targets
cargo test --lib --bin khaslana --quiet
cargo build --release
git diff --check
```

纯文档修改不要求编译。本次文档编写未重新运行 Cargo。测试数量和构建结果以最终集成检查为准；收尾修改发生前的通过结果不能自动视为后续修改的验证。

**自动化检查不能替代实机验收。** 本文不宣称所有界面完成双语视觉、交互或无遗漏验收。仍须在最终集成版本中实际检查语言切换、原生托盘、长驻通知和进度、模态与焦点、键盘/IME、深浅主题、窄窗、DPI 以及长英文截断与布局；AI 还需检查任务运行中切换偏好不改变既有任务语言快照。记录实际观察和未验证项，不把编译成功或资源已接入写成完整 UI 验收通过。
